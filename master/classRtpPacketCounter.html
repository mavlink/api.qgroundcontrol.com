Detailed Description

Counts one RTP stream's packets from their headers, as RFC 3550 (appendix A.1) has a receiver do, for a stream that no jitter buffer counts.

Lost packets are the sequence numbers missing between the first packet and the highest one, across the 16-bit wraparounds. A packet that arrives late is therefore no longer lost, and one that arrives twice counts once, both as far back as kReorderWindow packets.

A sender that starts over begins a new sequence: with another SSRC, or with sequence numbers too far from the last ones to be loss or reordering. Either way it starts with the second packet that goes on from the first, so a single stray packet changes nothing. The totals go on across sequences, without the packets lost between them, which nothing tells.

How far ahead is too far for loss follows the sender's packet rate, measured from the RTP timestamps: what it sends in kMaxDropoutSeconds, as rtpbin does (its "max-dropout-time").

Not thread-safe: the thread the packets arrive on adds them.

◆ kDefaultMaxDropout

int RtpPacketCounter::kDefaultMaxDropout = 3000
staticconstexpr

A packet this far ahead of the highest sequence number, or further, isn't the next one after a loss (RFC 3550's MAX_DROPOUT), while the packet rate isn't known: before a second of the stream, and without a clock rate.

◆ kMaxDropoutSeconds

int RtpPacketCounter::kMaxDropoutSeconds = 10

◆ kReorderWindow

int RtpPacketCounter::kReorderWindow = 1024
staticconstexpr

A packet less than this far behind the highest sequence number is a late one or a duplicate, which the packets seen there tell apart. RFC 3550's MAX_MISORDER, 100, is for audio's tens of packets a second, where video sends hundreds to thousands.
